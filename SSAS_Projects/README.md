# OLAP-куб (SSAS)

Курсова робота «Надвеликі бази даних», варіант 2 — «Оренда приміщень».

Проєкт Analysis Services Multidimensional `Rental_SSAS` будує куб **«Оренда»** над сховищем `RentalDW`.

## Склад папки

| Шлях | Що це |
|---|---|
| `Rental_SSAS/Rental_SSAS.sln`, `Rental_SSAS/Rental_SSAS/Rental_SSAS.dwproj` | Рішення та проєкт Visual Studio (Analysis Services Multidimensional) |
| `Rental_SSAS/Rental_SSAS/RentalDW.ds` | Джерело даних: `RentalDW` на `ANDRUSHA` (SQLOLEDB, логін `sa`, як у Lab1) |
| `Rental_SSAS/Rental_SSAS/RentalDW.dsv` | Data Source View: таблиці, зв'язки, іменовані обчислення та запити |
| `Rental_SSAS/Rental_SSAS/Dim *.dim` | 6 вимірів |
| `Rental_SSAS/Rental_SSAS/Rental.cube`, `Rental.partitions` | Куб: групи мір, MDX-скрипт, KPI, перспективи; партиції та агрегації |
| `MDX_QUERIES.mdx` | 10 демонстраційних MDX-запитів |

## Розгортання

1. Сховище `RentalDW` має бути заповнене (`SSIS_Projects`, пакет `Rental_ETL.dtsx`).
2. Відкрийте `Rental_SSAS.sln` у Visual Studio (від імені адміністратора, як і Lab1).
3. Solution Explorer → `RentalDW.ds` → **Edit…** → пароль `sa`, **Save my password**; Impersonation — **Use the service account**.
4. **Build → Deploy Solution** — база `Rental_SSAS` розгортається на `localhost` і обробляється (Process Full).
5. Перевірка — SSMS, підключення **Analysis Services** → `Rental_SSAS` → **New Query → MDX** → запити з `MDX_QUERIES.mdx`.

## 4.1–4.2 Data Source View

- **Таблиці:** 3 таблиці фактів (`Fact_Invoice`, `Fact_Payment`, `Fact_Occupancy`) і 5 вимірів сховища; зв'язки — з зовнішніх ключів (у т. ч. три ролі дати у фактах).
- **Named Calculations (28):** наприклад, `QuarterKey` / `QuarterLabel` / `MonthLabel` / `WeekLabel` / `DayTypeName` / `HolidayLabel` у `Dim_Date`; `PremisesLabel` / `VersionLabel` / `CurrentLabel` / `PriceCategory` / порядок категорій у `Dim_Premises`; `ContractStatus` / `DurationOrder` / `PeriodLabel` у `Dim_Contract`; `OverdueFlag`, `LateFlag`, `LateDays`, `OccupiedFlag` у фактах.
- **Named Queries (2):**
  - `Contract_Facts` — договір як факт (дата початку, орендар і приміщення з останнього рахунку, ставка, депозит, тривалість) — основа групи мір «Договори»;
  - `Payment_Timing` — довідник своєчасності оплати (Наперед / Вчасно / Із запізненням) з порядком сортування — основа виміру «Своєчасність оплати».

## 4.3 Виміри

| Вимір | Атрибути | Ієрархії | Особливості |
|---|---|---|---|
| **Дата** (Time) | Дата, Рік, Квартал, Місяць, Місяць року, Тиждень, День тижня, Тип дня, Свято, Робочий день | **Календар:** Рік → Квартал → Місяць → День; **Тижні:** Рік → Тиждень → День | Типи атрибутів Years / Quarters / Months / Days (потрібні для YTD, ParallelPeriod); у кубі три ролі: **Період** і **Термін оплати** |
| **Приміщення** (основна сутність) | Версія приміщення (ключ), Приміщення, Місто, Тип, Група типів, Поверховість, Категорія площі, Цінова категорія, Версія запису | **Географія:** Місто → Приміщення; **За типом:** Група → Тип → Приміщення | **SCD Type 2:** ключ — `PremisesKey` (версія), атрибут «Приміщення» об'єднує версії за `PremisesID`; властивості членів — адреса, площа, кімнати, поверх, ціна, діє з / до; обчислюваний член **«Комерційна нерухомість»** |
| **Орендар** | Орендар, Тип орендаря, Наявність email | **За типом:** Тип → Орендар | Властивості: податковий код, телефон, email |
| **Договір** | Договір, Тривалість, Стан договору, Рік підписання, День оплати | **За тривалістю**, **За роком підписання** | Властивості: орендна плата, депозит, період дії |
| **Статус рахунку** | Статус | — | Сортування за кодом статусу OLTP |
| **Своєчасність оплати** | Своєчасність | — | Сортування Наперед → Вчасно → Із запізненням |

Для всіх вимірів задано ключові атрибути, атрибутні зв'язки (у календарі — `Rigid`), Name Column і Order By (місяці, дні тижня, категорії сортуються за порядковим ключем, а не за алфавітом). Атрибути-властивості мають `AttributeHierarchyEnabled = false`.

## 4.4 Міри

| Група мір | Міри | Типи агрегації |
|---|---|---|
| Рахунки | Сума рахунків, Оренда, Комунальні, Пеня, Сплачено, Борг, Кількість рахунків, Прострочених рахунків, Мінімальний / Максимальний рахунок, Макс днів прострочення | Sum, Count, Min, Max |
| Платежі | Сума платежів, Кількість платежів, Мінімальний / Максимальний платіж, Платежів із запізненням | Sum, Count, Min, Max |
| Завантаженість | Орендовані дні, Доступні дні, Дохід від оренди, Договорів у місяці, Місяців з орендою | Sum, Count |
| Договори | Кількість договорів, Сума депозитів, Мінімальна / Максимальна ставка оренди | Count, Sum, Min, Max |
| Унікальні орендарі | Унікальних орендарів | **Distinct Count** |
| Унікальні приміщення | Орендованих приміщень | **Distinct Count** |

Середні значення (**Average**) реалізовано обчислюваними мірами Sum / Count — це рекомендований у SSAS спосіб: середнє коректно агрегується на будь-якому рівні.

**Обчислювані міри (22):** середній рахунок, середній платіж, середнє прострочення, середнє запізнення оплати, середня ставка оренди, середня тривалість договору; рівень оплати, частка боргу, частка прострочених рахунків, частка вчасних платежів, завантаженість, частка доходу від загального (% від загального), дохід на приміщення; YTD, PY, YoY, MoM, ковзні середні, рейтинги.

## 4.5 MDX-обчислення (`Rental.cube` → вкладка Calculations)

| Вимога | Реалізація |
|---|---|
| Time Intelligence | `Сума рахунків YTD`, `Сплачено YTD` (PeriodsToDate), `Сума рахунків PY` (ParallelPeriod), `Сума рахунків YoY`, `Сума платежів MoM` |
| Ranking | Набори `Топ-10 боржників`, `Топ-10 приміщень за доходом` (TopCount, DYNAMIC), міри `Місце приміщення за доходом`, `Місце орендаря за боргом` (Rank) |
| Moving Averages | `Платежі ковзне середнє 3`, `Завантаженість ковзна 3` (LastPeriods) |
| Бізнес-метрики | Рівень оплати, частка боргу, частка прострочених, дохід на приміщення, частка доходу від загального |
| KPI | **Рівень оплати рахунків** (ціль 95 %), **Завантаженість приміщень** (ціль 80 %), **Своєчасність оплат** (ціль 90 %) — значення, ціль, статус (світлофор: ціль / жовта зона / нижче) і тренд (стрілка, порівняння з попереднім роком) |
| Обчислюваний член виміру | `[Приміщення].[Група типів].[Комерційна нерухомість]` = Офіси + Торгівля та послуги + Склад і виробництво |

## 4.6 Оптимізація

- **Партиції:** `Рахунки` і `Платежі` розбито по роках (2021 … 2026, query binding з умовою на ключ дати). Попередження Best Practices «партиції менші за 2 млн рядків» очікуване: обсяг навчальний, партиції зроблено за вимогою ТЗ і для демонстрації.
- **Storage Mode:** історичні роки — **MOLAP** (дані й агрегати в кубі, найшвидші запити); поточний рік — **HOLAP** (агрегати в кубі, деталі читаються зі сховища, тож свіжі дані не потребують повної обробки куба). Групи Distinct Count, «Договори», «Завантаженість» — MOLAP.
- **Агрегації:** Aggregation Design Wizard з умовою *Performance gain reaches 30 %* для груп «Рахунки» (28 агрегацій), «Платежі» (35), «Завантаженість» (5). У трасі Profiler видно читання з агрегацій (`Started reading data from the 'Aggregation…'`).
- **Атрибутні зв'язки:** природні ієрархії (День → Місяць → Квартал → Рік, Приміщення → Тип → Група, Приміщення → Місто), `Rigid` у календарі, властивості без ієрархій.
- **Perspectives:** «Фінанси» (рахунки, платежі, борги, KPI оплати), «Нерухомість» (завантаженість, договори, рейтинги приміщень), «Керівництво» (ключові показники та всі KPI).

### Продуктивність (OLTP vs сховище vs куб), мс

Час SQL — `PERFORMANCE_TEST.sql` (холодний кеш — після `DBCC DROPCLEANBUFFERS`); час куба — SQL Server Profiler, подія **Query End** (холодний кеш — після XMLA `ClearCache`).

| Запит | OLTP холодний / теплий | Сховище холодний / теплий | Куб холодний / теплий |
|---|---|---|---|
| 1. Сума і сплачено по роках і групах типів | 110 / 62 | 54 / 23 | 143 / 3 |
| 2. Топ-10 боржників | 99 / 90 | 44 / 26 | 672 / 65 |
| 3. Завантаженість по містах і місяцях 2025 | 229 / 226 | 84 / 73 | 143 / 4 |

**Висновки:**
- Сховище в 2–3 рази швидше за OLTP: менше з'єднань, сплачене та завантаженість пораховані заздалегідь (ETL), а не з платежів і дат договорів під час запиту.
- Куб із теплим кешем відповідає за 3–65 мс — у 10–25 разів швидше за SQL, бо результати беруться з агрегацій і кешу.
- Холодний запит до куба повільніший на малому обсязі: витрати на завантаження агрегацій і звернення до HOLAP-партиції поточного року в SQL. Топ-10 боржників — найдорожчий, бо ранжує 50 тис. орендарів без агрегації по орендарю.
- Масштабування: зі зростанням фактів до мільйонів рядків час SQL зростає лінійно, а куба — майже ні (агрегації); поточний рік у HOLAP можна обробляти інкрементально (Process Add / Process Data лише останньої партиції).

### Резервна копія

`BACKUP_CUBE.xmla` (SSMS → Analysis Services → New Query → XMLA → F5) створює `Rental_SSAS.abf` у папці резервних копій SSAS (`…\MSAS16.MSSQLSERVER\OLAP\Backup`). Відновлення — SSMS → Databases → Restore.
